## Recommendation

After S00's complete source mapping and explicit source selection, start with **S02, versioned offer and customer-policy contracts**, as a narrow additive slice. It can define offers in the current authenticated single-workspace model without making up tenant IDs; S03 will decide how to add tenant ownership safely. Persist the offer version and proof metadata, then bind it to new Astra campaign launches through the existing immutable launch snapshot. Legacy campaigns stay valid with no offer reference; new Astra-bound launches require an approved version and current proof. If the binding cannot fit the current file ownership, implement only the independent contract/persistence part and label S02 partial until launch acceptance is actually covered.

S03 is the larger prerequisite and should follow as a migration design and then a separately reviewed code tranche. The newer application has no `tenant_id` or `workspace_id` on its shared business tables and no workspace table. Its current role system represents a single workspace, so tenant isolation requires a planned migration across the complete relationship graph, authorization, jobs, exports, caches and suppression semantics. A one-column retrofit would give a false impression of isolation and risk existing identity, send history, and opt-out state.

Do not start S04, S05, or X01 first. S04 depends on S03; S05 depends on S03 and S04; X01 depends on S00 and S05. Existing SQL transactions and job coordinators are useful implementation material but do not satisfy the proposed immutable event ledger, durable cross-restart orchestration, or a single harness contract.

## Current implementation evidence

The newer checkout is a Node application backed by a process-wide `better-sqlite3` singleton (`pipeline/database.js:16-44`). It enables WAL, foreign keys, a five-second busy timeout, and secure deletion. Schema initialization uses additive `CREATE TABLE IF NOT EXISTS` definitions and `runMigrations`; it has a `schema_migrations` table (`pipeline/database.js:1398-1444`). This is evidence of a mature local single-database application, not PostgreSQL, tenant RLS, or a versioned production migration framework.

Auth is substantial and should be retained: `pipeline/auth-manager.js:61-143` defines users, hashed sessions, roles, audit, invitations, MFA challenges and recovery codes; `currentSession` re-reads the current stored user (`:520-528`); role checks are deterministic (`:967-1000`). `server.js:2874-2882` authenticates API calls, verifies CSRF on writes and authorizes by role. Membership endpoints are under `/api/workspace/*` (`server.js:586-613`), but no `workspaces` / `workspace_members` relation was found in the DB schema. Authenticated member identity and role are not equivalent to a tenant scope.

The central domain tables are global: batches, leads, emails/evidence, suppression, mailboxes, campaigns, launches, sends, events, verification jobs, and import/discovery jobs contain no tenant/workspace key. Examples include batches and leads (`pipeline/database.js:56-64,179-220`), imports and job children (`:131-176`), discovery jobs (`:551-760`), suppressions (`:810`), usage (`:887-910`), campaigns (`:913+`), send rows (`:1032+`) and events (`:1102+`). Their foreign keys protect references within the shared database, but not ownership boundaries. Some user-managed saved searches/templates use `user_id` (`:684-709`); this is useful evidence of a narrow user-owned pattern, not complete tenant enforcement. Suppression is currently unique/global by address semantics and has intentional send-side effects; it needs explicit migration/privacy treatment, not casual copying into per-user lists.

There is meaningful durable-ish work infrastructure to reuse. CSV imports persist job status, upload offsets, chunk hashes, row cursor, counts, cancellation and rejections; recovery returns interrupted processing rows to queued (`pipeline/database.js:129-176`, `pipeline/contact-import-jobs.js:92-168,380-417,498-521`). Verification, website discovery, lead search and bounded lead discovery each persist parent/child state and provide recovery/control methods. The bounded lead-discovery coordinator composes existing search, directory, website and verifier services (`pipeline/lead-discovery-jobs.js:113+`); it already demonstrates that one coordinator should reuse existing workers. These are SQLite job records and local callbacks/timers rather than evidence of leases/fencing, multi-host durability, a transactional outbox, or one platform-wide workflow owner. There are separately implemented queues, so S05 must inventory each and name one owner before introducing another.

`events` stores application activity and replies, and campaign/click/delivery reporting has grown, but no append-only outcome ledger, schema-versioned event envelope, outbox/consumer receipt, correction lineage, or projection rebuild contract was found. Existing transaction helpers are useful (`better-sqlite3` transactions appear across auth and pipeline modules), but they do not establish event replay guarantees. Captured metrics also have limits: `/api` explicitly describes AI usage as observed call counts and leaves token/USD cost unknown pending per-request storage and dated rate cards (`server.js:352-367`).

Provider configuration is a major replacement candidate. `config/personalization.json` enables local Ollama, configures Bedrock, and sets `fallback_to_ollama: true`; `pipeline/lead-strategy.js` supports Ollama, OpenAI-compatible endpoints, and FreeInference, while `pipeline/ai-usage.js` accepts `ollama` and `bedrock` usage providers. This conflicts with the Astra/extension requirement that GLM-5.3 API is the only generative provider, including graders, and that hidden fallbacks be absent. No live provider was called; commercial, privacy, and endpoint gates remain open. Provider settings and any key material were not read.

## First bounded slice proposal: S02

Candidate ownership after current path conflicts are resolved:

- New `pipeline/offer-contracts.js`: pure validation and version construction for service/scope, evidence assets, bounded price authority and currency, exclusions/forbidden claims, geography/jurisdiction, egress policy, margin/capacity fields, lifecycle state, and canonical content hash. Proof assets need source, immutable reference/hash, observed/effective or expiry time, and status; an absent or stale proof fails closed. Material edits create a new version; approval/revocation is explicit and audited.
- `pipeline/database.js`: additive `offers` and immutable `offer_versions` schema and `campaigns.offer_version_id` nullable reference, with a reversible migration. Preserve existing IDs and campaigns; do not fabricate or auto-approve legacy offers. `NULL` means a legacy campaign outside the new Astra contract, not an implicit default tenant or inferred offer.
- `server.js`: authenticated owner/admin endpoints for create, version, approve/revoke, and read; carry the trusted session actor from the existing request middleware. Reviewer read access is optional; write authority must be explicit. No send side effects.
- `pipeline/sending-engine.js`: extend `buildCampaignLaunchSnapshot` to bind the approved offer version ID, canonical hash, policy version, and minimal proof metadata. Validate at queue/preflight that the version is approved and proof is current. Existing snapshot hashes already detect changes, so policy drift should prevent queueing and the send-time eligibility check must fail closed if current validity no longer matches. Keep the `offerVersion` snapshot section absent for legacy `NULL` campaigns so their established flows remain unchanged.
- New `tests/offer-contracts.test.mjs`: unit/API tests against temporary SQLite for schema boundaries, missing geography/proof, invalid price/currency, forbidden claims, stale/revoked versions, authorization, version immutability, DB reopen, and no send rows. Narrow additions to `tests/campaign-launch-snapshot.test.mjs` and `tests/campaign-preflight.test.mjs` verify exact offer/hash binding, no snapshot creation in dry-run, rejection before queue for missing/unapproved/revoked/stale proof, mutation/revocation after launch, legacy no-offer behavior, unchanged old IDs, and zero SMTP submissions on every rejected path.

The key acceptance is that invalid, unapproved, stale or revoked offer versions cannot enter a campaign launch snapshot; a material change creates a distinct version and invalidates authorization. Existing campaign launches already have the useful immutable JSON/hash invariant (`pipeline/database.js:921-937`; `pipeline/sending-engine.js:1056-1154`) and tests cover hash, exact copy, drift rejection, and legacy rows (`tests/campaign-launch-snapshot.test.mjs:113-167`). Preserve these checks and add offer lineage to the same snapshot owner; do not introduce a second approval or workflow state owner. `actor` is supplied from the trusted session into `handleSendingApi` (`server.js:2250`, caller near `:2932`); general role authorization permits operators to write and reviewers to read, so offer approval/revocation needs an explicit owner/admin check. The campaign/API/database and sending paths overlap historical ALL-TRACK-002 ownership entries. The coordinator must check the latest active assignment and transfer paths before editing them. `orchestration/OWNERSHIP.md` has multiple historical “current authorized ticket” entries; `AGENTS.md` says `orchestration/CURRENT_COLLABORATION.md` and `orchestration/REVIEW_QUEUE.md` are absent. Treat that as ownership to reconcile, not proof the paths are free.

Offer persistence created before S03 is explicitly single-workspace transitional storage. Do not add `tenant_id`, synthesize a default workspace, or claim multi-tenant offer isolation. S03 must plan how to attach these rows and preserve version/hash/approval/proof lineage in a reversible migration.

S03 should then inventory each table and relationship, establish a tenant/workspace identity and membership model, identify historical-data ownership and global suppression policy, and define reversible key/backfill strategy before source changes. Its acceptance must include adversarial cross-tenant API, job-ID substitution, cached lookup, import/export, and suppression tests. It must preserve existing IDs and lineage and must not silently assign legacy records to a fabricated tenant.

## Reuse / replace / unknown

- **Reuse:** existing auth primitives and role checks; current typed/evidence-rich domain records; transactional writes; the import/discovery/verifier workers and coordinator patterns; suppression checks; send claims and uncertain-submission quarantine; bounded campaign state; temporary-SQLite tests.
- **Extend or migrate:** all shared business rows and job records to tenant-safe ownership; auth user-to-workspace membership; job envelopes and context snapshots; event/outcome capture and cost reconciliation; campaign authorization from mutable approval toward immutable versioned scope.
- **Replace or remove under target contract:** SQLite singleton as the multi-tenant reference store if S03 proves it cannot meet compound-reference/isolation needs; local/Bedrock/multiple-provider generator selection and fallback with a sole GLM-5.3 gateway after S01; overlapping background schedulers only after S05 identifies the single durable workflow owner.
- **Unknown:** production DB contents and data volume; actual startup and scheduler topology in a deployed environment; whether backup/restore or tenancy controls exist outside this checkout; external provider commercial/privacy approvals; cross-tenant test results; production job recovery behavior; whether any separate runtime has durable queue infrastructure.
