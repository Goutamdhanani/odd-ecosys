# S01 commercial and source gate register

**Status: BLOCKED_EXTERNAL_UNKNOWN; acceptance: NOT_ACCEPTED.** This register records repository evidence and review questions. It is not an external approval, legal opinion, provider contract, or proof that application egress is controlled. Every unresolved/denied use remains disabled in the register. No private inference, customer-data access, live mailbox, paid call, credential read, or production action was performed for this increment.

The contract target is the exact provider/model pair `glm-5.3-api` / `GLM-5.3`. The existing local FreeInference tooling defaults to `https://freeinference.org/v1` and `glm-5.3-flash`; this is configuration evidence only, not account entitlement, contractual permission, or a match for the target. The application still contains Ollama/Bedrock and configurable-provider paths. The new helper is standalone documentation/tooling and is not called by those paths. It therefore does **not** close legacy egress or enforce the sole-provider rule.

## Provider and data processing questions

The FreeInference [Terms of Service](https://freeinference.org/terms) reviewed on 24 October 2026 state that the service is experimental/research oriented and routes may reach third-party model providers. They say prompts and responses may be logged, stored, hashed, redacted, or processed; logs and derived data may be used to operate, secure, debug, improve, and analyze the service; anonymized derived data may be published; and sanitization does not guarantee removal of sensitive information. The terms say not to submit sensitive personal, confidential, regulated, secret, credential, or unauthorized data. The official [security and retention documentation](https://doc.freeinference.org/agents/security) additionally says prompt/response logs are used for research and that beta conversations, task events, and sandboxes persist until permanent deletion while a formal retention policy is planned. These are risk findings for the currently configured aggregator route, not approval to submit application data.

The [Z.ai Terms of Use and Additional Terms for API Services](https://chat.z.ai/legal-agreement/terms-of-service), last updated 14 April 2026, describe API downstream integration rights and refer to a Data Processing Addendum. Their API terms address service-improvement opt-in for End User Content, necessary processing and subcontractors, and prohibit certain external-model optimization/training uses except for authorized integration with specific business scenarios. The repository does not establish that a direct Z.ai API agreement governs the FreeInference route. Both route and applicability require confirmation before relying on any Z.ai clause.

The machine-readable [register](commercial-gates.json) keeps these decisions individually unknown and disabled: commercial/downstream use; personal and confidential input processing; DPA and data roles; required model/provider disclosure; prompts, responses, metadata, research/logging, caching, retention, deletion and backups; upstream/subprocessor identities and processing regions; and any prompt/model optimization, training, labeling, fine-tuning, or external model development. No vendor signature, account-specific written approval, DPA, opt-out evidence, or subprocessor schedule was found in the scoped repository review.

## Source and mailbox scope

The repository has public website collection, EPCH member-directory and EEPC advisory fetchers, SearXNG search against a runtime-configured instance, OpenStreetMap export import, user-supplied CSV import, Reacher/Disify verification, DNS/SMTP probes, Meta Lead Ads, and a runtime-configured Twenty CRM endpoint. For each source the unresolved questions include its actual operator/publisher and applicable terms or license; permission for automated collection and commercial use; rate limits and attribution; cache/retention and deletion; resale or redistribution; and whether the data may enter a model prompt. Runtime `robots.txt` checks in selected crawlers are useful crawl controls; they are not a license or reuse grant. OSM rows carry an ODbL attribution label in source, but exact export provenance and resulting database/share-alike obligations still require review.

Google code verifies an ID token with Google’s fixed JWKS endpoint and consumes `sub`, `email`, `email_verified`, and optional `hd`; it does not request a Google OAuth access token or Gmail API scope. Current mailbox receive uses stored IMAP host/user/password credentials. No Gmail delegated-mailbox scope is implemented or approved. Before any mailbox OAuth work, record the exact least-privileged scope per operation (for example, read, modify/labels, or send only if required), the API access model and any verification process, and token storage, access, retention, and revocation controls. The register deliberately invents no scope grant.

`commercial-gates.json` now snapshots all **151** `node_modules` paths in the current `package-lock.json` v3 (`8dbd87c0fc8e92ca65ed04ffac614b6c86aaa52364c766d1d3ca4d4cc9571738`). For each path it stores the exact version and lock integrity, the installed `package.json` SHA-256/declaration when present, and hashes/byte lengths for package-directory `LICENSE`, `LICENCE`, `COPYING`, and `NOTICE` files found. The audited Windows install has 11 locked paths absent locally; one installed package has no license declaration, and 23 installed paths have no selected license text file. This is a reproducible local inventory, not legal review. The root package declares MIT, which does not replace dependency terms.

The current Windows install has 11 lockfile entries absent on this host (10 optional platform-specific canvas packages and `fsevents`), so their actual license metadata/text was not inspected here. Installed `mailcheck@1.1.1` has a LICENSE file but its package metadata has no license expression, so its expression remains `UNKNOWN`. `@zone-eu/mailsplit@5.4.20` declares `(MIT OR EUPL-1.1+)`, which needs a human choice/review. Ten other installed paths have a declared expression but no selected license text in that package directory. None of these facts is silently resolved by the root MIT field.

## Local gate helper and test boundary

`tools/astra/commercial-gates.mjs` can evaluate only the exact target provider/model and an explicitly supplied `synthetic-fixture` classification. It requires current, unexpired, evidence-backed entries for every provider decision needed by the inference operation; missing, unknown, disabled, malformed, expired, or unsupported entries deny before the supplied callback. Because this register is editable and the helper has no application call sites, an `approved` field alone is not proof of a real approval; external reviewer identity and evidence authenticity remain outside this helper.

`S01-B01` checks the lockfile pin coverage, installed metadata/text fingerprints, unknown and dual-license cases, scope/unknown statuses, and absence of fabricated approvals. `S01-B02` uses a local counting callback only: it verifies private data, unresolved provider terms, and a non-target provider leave the callback uncalled. No callback performs network or inference. This is not a live contract test, private-data test against a vendor, app egress test, or evidence that the application currently observes the helper.

No database or source schema migration is included. Rollback for this documentation/tool-only increment is removal/revert of the added register, helper, focused test, and S01 evidence files; no runtime state or application behavior is changed. S01 remains blocked until externally sourced, applicable evidence resolves the required decisions, the application gateway is separately integrated and tested, and an independent Luna review verifies the exact candidate.
