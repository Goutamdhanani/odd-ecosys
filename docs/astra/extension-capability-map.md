## Foundation and harness reuse candidates

The strongest reusable foundation is the existing durable job pattern. `pipeline/lead-discovery-jobs.js` coordinates work and stops child work on its runtime limit; `pipeline/website-discovery-jobs.js` and `pipeline/epch-directory-jobs.js` persist task attempts and recover interrupted work; `pipeline/contact-import-jobs.js` has resumable chunk state. These are useful examples for an adapter and recovery contract, but each module owns its own job state. X01 still needs one selected workflow-state owner and a context manifest. A first harness slice should wrap one of these owners and reference its existing records instead of creating a second workflow ledger.

`pipeline/auth-manager.js` and the server's workspace routes provide an existing authentication and role boundary. `pipeline/ai-usage.js` provides a durable, prompt-free provider usage record. `pipeline/sending-engine.js` provides immutable campaign launch snapshots and an uncertain-send recovery rule. Reuse is plausible for tenant authorization, request accounting and side-effect reconciliation after the relevant S-task contracts are verified.

The limits are material: there is no common HarnessTask/Result contract or shared immutable context manifest; the generative route currently supports Ollama and Bedrock, with a Bedrock-to-Ollama fallback, while the extension requires a GLM-5.3-only route including graders. Existing job budgets are vertical-specific. So the best early implementation candidate, once the baseline and prerequisites are selected, is a thin harness adapter around one existing durable job manager, with explicit state ownership, context references and budget accounting. It should not declare X01–X03 complete until their cross-tenant, no-duplicate-owner, forbidden-tool and crash-recovery acceptance is exercised.

## Cross-task contract and dependency amendments

The extension updates existing work in several important ways. S05–S07 need one harness contract, bounded progress, provider/grader allowlists and reservations. S13/S14 need separate support, uncertainty, event-specific probability, utility, risk and reversibility fields with explicit ACT/BLOCK migration. S19–S21 need campaign authorization envelopes, routine in-scope automatic sending, optional draft mode, exception handling and replay-safe server-issued tickets. Per-message approval must not become a permanent blanket requirement. S23/S28/S29 need versioned skills and optimizer-independent release tests. S25/S32/S34 need full engagement metrics, one privacy-filtered telemetry route and measured marginal costs. S26 needs the Inspect adapter and H0–H3 benchmark.

**Add X14 as a required dependency of S33** for authorized pilot/cutover. X16 stays optional P2, after X04 and X14, and outside initial launch. Campaign-scoped routine automation is the target; per-draft review remains an optional operating mode. Preserve the existing suppression, verification, sender and uncertain-submission safeguards during any future implementation.
